# 巡回点検報告

Google Drive「物件定期巡回／点検チェックシート.xlsx」を元に、物件設定と各回の点検結果を分離します。職員名・利用者名・住所の入力欄は作りません。作成者・訂正者はアカウントIDで記録し、顧客には役割だけ表示します。

## 物件の設備と点検対象

管理者が物件管理の「点検対象を設定」から、屋根・壁・柱・窓・ベランダ・フェンス／塀・排水路／浄化槽・庭木の8区分について「あり／なし／未設定」と通常点検するかを設定します。設備ありで点検対象外なら理由が必要です。未設定が残る物件では、新しい巡回報告は作成できません。

雑草・ゴミ・害虫・動物、侵入の形跡・焼け跡、郵便物は毎回の対象に含めます。設備がないことと、その回だけ確認・作業できなかったことは区別します。

点検マスタは40項目で、建物7区分×4種類の異常、庭木5項目、外構4項目、危険事項2項目、郵便物1項目です。マスタはバージョン付きIDを持ち、通常クライアントから改変できません。項目の意味や名前を変える場合は新バージョンを追加して既存のマスタを保持します。

## 作成・下書き・公開

作業報告の登録から物件を選び、作業日・開始終了時刻（日本時間）・本文・点検結果・写真・実費を入力します。「未確認」は初期値で、「無し」と同じ扱いにはしません。

- 各項目は結果を選ぶか、「今回未実施」と理由を記録します。
- 作業全体が未実施の場合は全体の理由を記録します。開始終了時刻は省略でき、理由を各項目に重複保存しません。
- 通常の巡回報告を公開するには開始終了時刻が必要です。未確認項目が残る場合は公開できません。
- 下書きは管理者と作成した職員だけ閲覧でき、顧客や他の職員には非表示です。
- 顧客は自分の物件の公開済み報告・結果・写真・実費だけ閲覧できます。下書きの実費は請求作成の対象にもなりません。

最初に下書きと実費をトランザクションで保存し、写真をアップロードしてから写真一覧と公開状態を保存します。アップロードや公開に失敗しても下書きが残り、報告一覧から再編集できます。写真は合計10枚、1枚10MB以下のJPEG／PNG／WebPです。公開前のアップロード写真は顧客には見せません。

報告作成時点で対象だった項目IDを `report_inspection_results` の行として保持します。後で物件設定を変更しても、過去の報告の対象を追加・削除しません。ラベルなどはバージョン固定マスタを参照し、報告ごとには重複保存しません。

既存の報告は公開済みとして維持します。過去の自由文報告にチェック結果を推測で追加することはありません。既存報告も本文・日時・写真・実施状態を訂正できます。

## 訂正と履歴

管理者はすべて、職員は自分の報告を編集できます。保存ごとに編集理由が必須です。表示時のリビジョンが古ければ上書きせず、開き直しを求めます。内容・チェック結果・写真・履歴を1トランザクションで更新し、失敗した場合は戻します。

編集履歴には日時・操作者IDと役割・理由・変更した項目の変更前後を保存します。各チェックは項目ID単位で差分を記録します。報告の作成日時・作成者・物件と作成時の対象項目は訂正で変更しません。通常クライアントから履歴の書換え・削除はできません。

下書き中の編集も記録しますが、顧客には公開前の編集履歴を見せません。初回公開は訂正通知を出さず、公開済み報告の編集を1保存＝1件の訂正としてコミュニケーションへ表示します。対象報告へのリンク `#report-<ID>` で物件を選択して該当報告を表示します。

各報告の下部に「報告の編集履歴」を折りたたみ表示し、変更項目ごとに変更前後を展開できます。写真を外しても、過去の写真はストレージと履歴に残し、権限を確認して署名URLを発行します。現在の報告または履歴に参照される写真は通常操作で削除できません。未参照のアップロードだけを片付けられます。

実費の変更は、PR #15の実費管理・専用RPCを引き続き使用します。報告の訂正からは実費を重複登録せず、公開後の実費訂正と有効な請求情報への同期は従来どおりです。報告の下書き中に行った実費訂正も顧客には通知・表示しません。

## 保存先と公開順序

- `inspection_subjects` / `inspection_items`：バージョン付きの共通マスタ。
- `property_inspection_profiles` / `property_inspection_targets`：物件の設備・対象設定。
- `reports`：作成・公開・版番号・実施状態・開始終了日時。
- `report_inspection_results`：作成時の対象項目IDと今回の結果・理由・メモ。
- `report_revisions`：変更した項目の変更前後・理由・日時・操作者。

まずPR #15の `20261028224011_expense_corrections.sql`、次に `20261028225758_patrol_inspection_reports.sql` を適用し、その後フロントエンドを公開します。既存のマイグレーションを一括で再実行しません。既存報告への直接登録・写真更新・削除と旧登録RPCを止め、専用RPCへ集約するため、公開後は画面を再読み込みしてください。本番への適用は別途行います。

## 検証

`npm test` はPGliteに旧形式データを作成して新SQLを適用し、物件設定、対象保持、下書き非公開、未実施・理由・未確認の検証、訂正の権限・競合・原子性、写真と履歴の保持、請求対象の分離を検証します。

実アプリ画面のローカル結合確認用に `node tests/patrol-test-server.mjs` を起動できます。これはlocalhostの54321番だけで動く使い捨てPGliteサーバーで、本番Supabaseには接続しません。admin / worker / customer / other の架空IDで、任意のテストパスワードを使います。本物の認証を代替するための開発用フィクスチャであり、公開しないでください。

別ターミナルで次を実行すると、実アプリをこのフィクスチャへ接続できます。

```bash
VITE_SUPABASE_URL=http://127.0.0.1:54321 VITE_SUPABASE_PUBLISHABLE_KEY=fixture-public-key npm run dev -- --host 127.0.0.1 --port 5193 --strictPort
```

本番の環境変数・キー・認証状態は使いません。終了時には両プロセスを停止します。

PythonのPlaywrightとChromiumが利用できる環境では、`python tests/patrol-browser-check.py` で両サーバーの起動・終了を含む一連の画面確認を自動実行できます。設備設定、下書きの非公開、写真送信失敗後の再送、公開、訂正リンク・履歴・過去写真、全体未実施、モバイル表示、保存中のアカウント切替を確認します。54321番と5193番を空けて実行してください。
