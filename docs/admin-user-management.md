# 管理者画面のユーザー管理

登録・役割変更・利用停止／再開・パスワード再設定・削除を管理者画面から行います。ログインIDと顧客番号は発行後に変更しません。氏名・住所・実メールアドレスは入力しません。内部メールはログインID@example.comです。

## 公開手順

1. 003まで適用済みのSupabase SQL Editorで `supabase/migrations/20261018110758_admin_user_management.sql` を一度だけ実行します。既存のユーザーや業務データは削除しません。
2. Supabaseの `admin-users` Edge Functionを公開します。関数内で検証済みJWTと最新のDBの管理者権限を照合します。プラットフォームのJWT検証は無効にしますが、匿名で管理操作を受け付けるわけではありません。
3. 対応フロントエンドを公開します。Supabaseへの設定が完了するまでは、既存の運用画面をそのまま使います。SQL適用後は旧画面の利用停止ボタンは動かなくなるため、新版も続けて公開してください。

接続済みツールから公開できない場合、作業フォルダのターミナルで次を実行します（CLIは2.121.0で確認）。ログイン用トークンをチャットに貼る必要はありません。

```powershell
npx --yes --cache .npm-cache supabase@2.121.0 login
npx --yes --cache .npm-cache supabase@2.121.0 functions deploy admin-users --project-ref bwydtrphjvfiufhqxhzj --no-verify-jwt --use-api
```

関数は `supabase/functions/admin-users/` のindex.ts、handler.ts、deno.jsonで構成します。Supabaseの組み込み `SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` をサーバー内で使います。秘密キーをVercelのVITE_変数やソースコードへ追加しないでください。

## 操作と制限

- 初期パスワード・再設定パスワードは12～128文字で指定します。サービス側のパスワード強度設定も適用されます。電話／書面で本人確認して渡してください。画面で現在のパスワードを閲覧することはできません。
- 顧客からスタッフへの役割変更は、契約物件がある場合は拒否します。顧客と物件の紐付けが壊れないようにするためです。
- 自分自身の役割・停止状態・パスワード・削除はこの管理画面から変更できません。本人の再設定が必要な場合は、別の管理者またはSupabase管理画面で対応します。
- 削除は履歴を維持する論理削除です。profiles.deleted_atを設定し、activeをfalseにし、Authを長期停止します。認証レコード・ユーザーUUID・登録ID・顧客番号・物件・報告・依頼・メッセージは消去しません。削除済みIDは再利用できず、画面から復元できません。
- 削除前には対象のログインIDを確認入力します。「削除済みも表示する」で履歴上のアカウントを確認できます。
- 権限変更・停止・削除・パスワード再設定より前に発行したJWTは、current_roleで拒否します。変更と同じ秒に発行したJWTも拒否するため、変更直後の再ログインは1秒以上経ってから行います。古いログイン画面を使っているユーザーは再読込が必要です。
- APIとDBの更新は別サービスのため完全な単一トランザクションにはなりません。作成途中はAuthを停止し、失敗時には新規作成アカウントを除去します。状態変更時は先にDB権限を閉じ、Auth側の反映に失敗した場合はエラーを表示します。同じ操作を再実行できます。

## 検証

`npm test` はHTTPハンドラーの権限・入力・失敗時処理をモックで検証し、DBの権限・JWT失効・削除時の履歴保持をローカルPostgreSQLで確認します。`npm run build` はフロントエンドとサーバーハンドラーを型チェックします。実プロジェクトでの公開・疎通確認は別途必要です。

公開後は、テスト用ユーザーを作成→本人のログイン→役割変更・停止・再開→パスワード再設定→削除の順に確認します。削除後にログインできないことと、過去の業務履歴が残ることも確認します。実データのあるアカウントを動作テストのために削除しないでください。
